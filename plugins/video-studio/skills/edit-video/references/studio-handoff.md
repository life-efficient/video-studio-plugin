# Studio production handoff

Use the hosted, authenticated production tools for a shared Studio. The source-checkout adapter is described separately in [local checkout handoff](local-studio-handoff.md); use it only when the intended Studio is actually that local app. Copying an export into a local directory does not deliver it to the hosted app.

## Prepare and preserve

1. Read the exact video's latest version, feedback, recordings, and current readiness from Studio. A revision uses the latest delivered version and its matching editable project. Resolve comments referring to older versions against those versions.
2. Prefer the authenticated MCP bridge: call `prepare_edit` for the exact video and save the returned manifest locally. Call `read_edit_file_chunk` for its files through the same connection and route the structured results directly into files, never conversation text. The packaged runner at `<PLUGIN_ROOT>/packages/local-runner/video_studio.py` provides `stage` and `receive` to validate these transfers; use its `--help` and packaged README for the installed interface.
3. Run `prepare --manifest <MANIFEST_JSON> --assets <DOWNLOADED_ASSETS> --workspace <NEW_DIRECTORY>`. Verify downloaded asset identities and editable project correspondence before changing anything. A direct transfer is optional where supported: `create_edit_session` returns a short-lived, video-scoped connection for `--session-file <PRIVATE_SESSION_FILE> prepare --video <VIDEO_ID>`. Store its response outside snapshots and version control, never print credentials, and do not bypass an outer hosting authentication gate.
4. For a downloaded portable baseline, run `import-version --snapshot <DOWNLOADED_ZIP> --workspace <WORKSPACE> --version <LATEST_VERSION>` to install its verified immutable version folder, then `restore` its snapshot into a separate editable directory. Recovered older project files are downloaded under `legacy/<relative-path>` and recordings under `recordings/`; files in `legacy/` are recovery material, not registered portable baselines. A legacy project without a matching portable snapshot needs a correspondence check and explicit recovery before a faithful revision. Do not move a recovered `versions/` directory over the new workspace's immutable version folders. Work only in the new writable copy. Preserve the prior delivered snapshot. Use `snapshot --workspace <WORKSPACE> --version <NEW_VERSION> --project <PROJECT_DIRECTORY> --parent <BASE_VERSION>` to preserve portable editable inputs. Omit parent for a first cut. Include source code, timelines, dependencies, fonts, and assets needed for reproduction; do not include cache files, credentials, session files, or unrelated material. Large shared originals must have recorded identities and stable authorized retrieval.

## Deliver and verify

1. Complete silent visual and technical review. Use concrete change notes that state what changed and why. For a first cut, explain the editing choices. Preserve user feedback, prior versions, and server-owned timestamps. Do not add an iteration kind or descriptive label.
2. Run `deliver --plan-only --workspace <WORKSPACE> --version <NEW_VERSION> --export <RENDER_PATH> --notes <CHANGE_NOTES>`, using repeatable `--recording <ID>` arguments for recordings actually present in the export. Use repeatable `--clip '{"id":"stable-id","label":"Readable name"}'` arguments for additional source clips, retaining provenance in the editable project. Omit `--recording` when no recorded take was used. Never count unused takes or references studied only for style. Consult `deliver --help` rather than guessing arguments.
3. Use the plan's exact arguments to call `begin_edit_upload`, send each file through sequential `write_edit_upload_part` calls using programmatically generated chunks, and finish with `complete_edit_upload` through the authenticated MCP connection. Do not put base64 payloads in chat or tool logs. Direct session upload may be used only where tested and supported. Delivery must upload the rendered video and the matching editable snapshot, register the resulting version as ready for review, and return its stable Studio identity. Do not treat a successful file upload, chat download link, or local version name as proof of registration. If a transfer or registration fails, retain the workspace and report the exact incomplete step; do not silently fall back to recording storage.
4. Save the completion response locally alongside the upload plan to retain the Studio export identity and snapshot mapping. Read back the live export listing and verify version identity, media size, change notes, source IDs, and editable snapshot mapping. Fetch media metadata or a range/chunk silently to confirm availability. Where browser access is available, inspect the Editing card, source list, notes, and download link without playing it. Report an unavailable browser check honestly.
5. Keep the video in Editing and the new iteration ready for review. The reviewer decides when comments are ready for editing or when the video advances. Never infer readiness merely from comment presence.

## Version names

Read `latestVersion` from the prepared Studio manifest. Local version folders use that same number: import `v003` for Studio version 3, then preserve and deliver `v004` with `--parent v003`. A first cut starts at `v001`. The server checks the next number and rejects stale concurrent deliveries. Never guess a version from a render filename, renumber old iterations, or bypass a conflict. If another editor delivers meanwhile, refresh the live state and reconcile before making a new version. Keep each delivered snapshot immutable and retain its returned Studio export identity for the next editor.
